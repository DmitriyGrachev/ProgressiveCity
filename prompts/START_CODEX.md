# Задание Codex: реализовать Progress City MVP

Ты работаешь в папке моего нового проекта. Создай работающую первую версию приложения, а не только проектный план, каркас или красивый дашборд. Продуктовую идею я уже согласовал; разрешаю реализацию описанного ниже MVP. Обычные обратимые технические решения принимай сам и фиксируй коротко. Не заканчивай ответ предложением «могу приступить» и не проси повторно одобрить каждый этап.

## Сначала прочитай

1. `AGENTS.md` — правила работы, сохранность, проверки и ограничения.
2. `docs/MVP_SCOPE.md` — точный объём первой реализации.
3. `docs/CONCEPT.md` — контекст и смысл продукта; будущие идеи оттуда не расширяют автоматически текущий MVP.

Проверь существующую структуру, git status при наличии Git, Node/npm и lockfile. Не удаляй мои файлы ради scaffolding. Это локальный frontend-проект; Docker не нужен, тесты запускать нужно.

## Что создаём

Личный город-конструктор, который развивается из реального обучения, проектов и привычек. Пользователь начинает с одной мастерской, работает с ней, затем строит районы и целый город. Вблизи — конкретный результат; издалека — накопленный путь. Cities: Skylines — ориентир для свободы планировки, не требование повторять его графику, бренд, ассеты или экономическую симуляцию.

Районы имеют произвольный пользовательский смысл, не только Java/Python/ML. Содержание здания — мои заметки, схемы, изображения, код, источники и история. Можно вернуться к материалу через карту и поиск. Заметки и прогресс остаются, даже когда я переставил или убрал дом.

Главный цикл:
**исследовал/попробовал → сохранил свой результат → подтвердил один раз → получил возможность развития → сам выбрал улучшение/планировку → позже вернулся к материалу.**

## Технический выбор

TypeScript strict, React, Vite, PixiJS/WebGL, Zustand, Tiptap, Dexie/IndexedDB, Vitest, Playwright, CSS Modules/обычный CSS. Совместимые актуальные версии проверь по официальным источникам и peer dependencies. Для PixiJS допустима небольшая изолированная интеграция в React; `@pixi/react` используй только после проверки совместимости. Не добавляй Next.js/SSR или backend без необходимости. Зависимости должны иметь понятное назначение; безопасная библиотека валидации и ZIP допустимы.

Сначала выбери устойчивый изометрический рендеринг, а не полноценное 3D. Карта должна реально редактироваться: pan/zoom, выбор, перенос, проверка занятости, удаление с карты без потери данных, районы, дороги, декор, варианты зданий. Заработанные этапы отличай от свободного оформления.

Держи доменные правила и данные отдельно от сцены. Не создавай фреймворк для будущих микросервисов. Код организуй по понятным функциональным частям: город, направления/активности, заметки, история, хранение/резервирование.

## Как должен ощущаться интерфейс

Центр приложения — большая интерактивная карта. Панель материалов открывается по необходимости и не отнимает у города весь экран. Русский интерфейс, понятные подписи, контекстная панель здания и простая библиотека.

Начни с небольшого цельного визуального набора: разные силуэты зданий, крыши, окна, дорожки, озеленение, несколько согласованных цветов. Можно использовать собственные SVG/векторные ресурсы; не копируй коммерческие игровые ассеты. Кубическая болванка, случайные эмодзи на клетках или один фон с наложенными кнопками не считаются итоговой реализацией города. Не делай прежний футуристический mockup и не трать работу на генерацию концепт-арта.

Нужны хорошие пустые состояния, доступное управление, понятный предпросмотр допустимого размещения, отсутствие перекрывающих друг друга панелей. Изменения после реального результата должны быть заметны. Не показывай выдуманные streak, достижения и статистику. Демо — только явно отдельное.

## Этапы реализации

Составь краткий `docs/IMPLEMENTATION_PLAN.md` с проверяемыми этапами, затем сразу переходи к работе. Это последовательные этапы одной задачи, а не запросы новых согласований.

**A. Рабочий сквозной срез.** Запуск приложения, схема данных, одно направление и мастерская, редактируемая заметка, подтверждение результата, одно улучшение, перезагрузка без потери. Критические правила начни с тестов.

**B. Конструктор.** Реальное размещение и перенос, камера, занятость клеток, районы, дороги/декор, три типа зданий с этапами, пользовательские названия и оформление. Проверь hit testing при разном масштабе и порядок перекрытия объектов.

**C. Материалы и привычки.** Изображения как стабильные вложения, код, ссылки, теги, поиск, поддерживаемые и сокращаемые привычки, календарные даты, настройка правил с версией. Обеспечь сохранение перед сменой записи и отсутствие двойных наград.

**D. Накопленный путь и сохранность.** Неизменяемые снимки прошлого города, просмотр истории, экспорт/импорт архива с вложениями, валидация до замены, обработка ошибки записи/квоты и повреждённых архивов.

**E. Реальная проверка.** Пройди основной сценарий в браузере, запусти все проверки, исправь существенные проблемы, затем оформи передачу проекта пользователю.

Обновляй `docs/STATUS.md` по завершении этапов: сделано, проверки с фактическими результатами, известные проблемы и следующий шаг. Если контекст/окружение исчерпаны, оставь продолжабельное состояние и честный список недоделанного, не называй его полностью готовым MVP.

## Критические проверки

Проверь как минимум:

- Повторное подтверждение одного activity и повторное улучшение не дублируют начисление/списание. Текст можно редактировать без выдачи награды. Две вкладки не обходят правило.
- Заметка с изображением восстанавливается после reload и полного экспорта/импорта; в базе нет вечного сохранённого blob URL.
- Перенос и снятие здания не уничтожают материалы. Архивирование направления не удаляет его данные неявно.
- Нельзя поставить объект поверх занятого места или за пределами карты. Pan/zoom не ломают выбор и координаты.
- Настройка правил не переписывает предыдущие события. Расходы и начисления атомарны; ошибки записи не выглядят успехом.
- У привычки нет второй награды за ту же локальную дату; пропуски и сокращаемые привычки не разрушают город.
- Прошлый снимок не меняется после перестройки сегодняшнего города. История города не выдаётся за историю всех редакций заметок.
- Повреждённый или неподдерживаемый архив отклоняется до изменения базы. Импорт не начисляет награды повторно.
- Поиск реально находит сохранённый текст и не зависит от текущего положения здания.
- При быстрых переходах между заметками последнее изменение не теряется.

Создай scripts и фактически запусти:
`npm run lint`, `npm run typecheck`, `npm run test:unit`, `npm run test:e2e`, `npm run build`.

Проверь интерфейс через доступный браузер/Playwright: не только тестовые assertions, но и видимый город, панель заметок, масштаб, ошибки консоли. Сохрани несколько настоящих screenshots с синтетическими данными для ревью. При невозможности запустить браузер укажи точную причину; не заменяй проверку выдуманными результатами.

## Ограничения работы

Не коммить, не пушь, не создавай PR и не деплой: это сделаю я. Не трогай мои глобальные настройки, не снимай sandbox, не меняй права сам себе. Разрешение на установку необходимых локальных зависимостей и браузера запрашивай штатным способом при необходимости. Не используй ключ OpenAI API и внешнюю отправку личных заметок.

Не добавляй AI-тьютора, Spring backend, аккаунты, синхронизацию, marketplace, native-обёртку и сложную экономику. Не откладывай обязательное локальное сохранение, кастомизацию, заметки и резервный экспорт ради эффектного оформления.
