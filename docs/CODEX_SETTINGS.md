# Codex: настройки для Progress City

Проверено по официальной документации 7 сентября 2026 года. Это рекомендуемая конфигурация для данного проекта, а не универсальный оптимум. Доступные модели/пресеты зависят от аккаунта, клиента и этапа развёртывания [S1].

## Модель и reasoning

Моя рекомендация: **GPT-6 Astra, High** для первого многошагового прохода. В CLI ID модели — `gpt-6-astra`; усилие — `high`. Astra входит в текущие рекомендации Codex; её карточка подтверждает `low`, `medium`, `high` и `xhigh` [S1, S2].

Для последующих небольших изменений я бы выбирал Astra Medium; для трудного независимого ревью или устойчивой ошибки — временно Extra High (`xhigh`). При недоступности Astra — GPT-5.6 Sol (`gpt-5.6-sol`) с High. Это рабочая эвристика, не обещание качества и не измеренный бенчмарк нашего приложения. Sol указан среди рекомендованных моделей [S1].

Не переносить название режима ChatGPT Pro в поле `model`. Не предполагать, что максимальный reasoning нужен каждой правке. Я бы оставил стандартную скорость, не настраивал вручную размер контекста/temperature и не включал экспериментальные флаги для первого запуска. Точный остаток лимитов проверяется в своём аккаунте; в комплекте нет обещаний стоимости или числа запусков.

## Приложение и авторизация

Работай в локальной папке проекта, в режиме Codex с правом редактирования, не в read-only обсуждении и не только в режиме планирования. Войди своим ChatGPT-аккаунтом. Отдельный платный API-ключ для этого процесса не требуется; доступ через ChatGPT описан в официальном руководстве [S7].

Обнови используемое приложение/CLI до актуальной доступной версии. В расширенном выборе модели проверь выбранные модель и reasoning; автоматические Power-пресеты могут отличаться между аккаунтами [S1]. Не пытайся исправить отсутствие доступа к модели расширением прав на файловую систему.

## Файл проекта

В архиве уже есть `.codex/config.toml`. Он задаёт модель и High, запрос согласования `on-request`, согласование человеком, `workspace-write` и поиск `live`, а исходящий доступ из sandbox-команд оставляет выключенным. Эти параметры описаны в справочнике [S3].

Проектный конфиг действует для доверенной папки; глобальный обычно находится в `~/.codex/config.toml` (на Windows — `%USERPROFILE%\.codex\config.toml`). Запускай новую задачу из корня проекта после ознакомления с файлами. Явно переданные параметры запуска могут иметь более высокий приоритет [S4].

**Не заменяй весь глобальный конфиг.** В комплекте нет API-ключей, собственных провайдеров и локальных абсолютных путей.

**Существующие permission profiles:** `default_permissions` нельзя сочетать с `sandbox_mode` и `[sandbox_workspace_write]` [S3]. Если твой текущий конфиг уже использует такой профиль, не накладывай схемы друг на друга. Сохрани его рабочий вариант с доступом только к workspace, а из комплектного файла убери `sandbox_mode` и весь блок `[sandbox_workspace_write]`; перенеси только модель, reasoning, web search и политику согласования. Не меняй корпоративные ограничения.

`on-request` оставляет штатные запросы для действий за разрешённой границей; это не запрос на каждую обычную правку в проекте. Разрешения для поиска документации и сетевых shell-команд различаются. Поэтому поиск может работать, а скачивание npm-пакетов или браузера потребует отдельного согласования. Не выдавай бессрочный Full Access ради одной установки [S3, S8].

## Windows

Для нативного Windows при штатной настройке sandbox предпочтителен `elevated`. В официальной документации так называется более сильная изоляция с отдельными ограниченными пользователями, а не разрешение агенту делать всё [S5].

Этот системный выбор лучше оставить на уровне пользователя/штатного мастера настройки. При необходимости фрагмент для существующего `%USERPROFILE%\.codex\config.toml`:

```toml
[windows]
sandbox = "elevated"
```

Не добавляй второй `[windows]`, если такой раздел уже есть: поменяй только соответствующий ключ. Подготовка этой изоляции может запросить согласие администратора. Не запускай весь Codex с неограниченными правами. При WSL этот нативный Windows-параметр не нужен [S5].

## Правила, инструменты и запуск

`AGENTS.md` лежит в корне и содержит постоянные проектные договорённости; Codex читает такие файлы в начале работы [S6]. Вся концепция вынесена из него в `docs/`, чтобы постоянные инструкции не разрастались.

Для первого этапа я рекомендую одного основного агента. Достаточно файлов, терминала, поиска документации и браузерных проверок Playwright; дополнительные MCP не обязательны. Если уже доступны frontend/testing skills, промт разрешает их использовать, но не делает установку новых плагинов условием запуска.

Не разрешать публикацию, коммиты, пуши, деплой и изменения глобальных настроек: пользователь делает это сам. Разрешить необходимые локальные установки и проверки через штатные запросы. Приложение должно проходить тесты без Docker.

Первое сообщение — содержимое `prompts/START_CODEX.md` либо короткий запуск из START_HERE.md. Отдельный read-only промт ревью находится в `prompts/REVIEW_BEFORE_GITHUB.md`.
