# Архитектура и принятые решения

## Сравнение города — 20.09.2026

`domain/comparison.ts` — чистое сопоставление визуальных состояний. Учебная постройка получает ключ по `learningObjectId`, привычка — по `trackId`, декор — по ID размещения. ID здания не участвует в идентичности исследования. Независимые признаки допускают сочетание этапа, переноса и оформления; наличие только в A/B означает снятие/появление **на карте**. Районы сопоставляются по ID и относятся к декоративным изменениям. `snapshotLayout` копирует геометрию и исторические этапы, используется также прежней командой создания снимка; формат Snapshot не менялся.

`storage/comparison.ts` читает epoch, город, снимки, размещения, районы, владельцев, события и результаты в одной readonly-транзакции Dexie. `ComparisonSession` хранится в памяти Zustand. Текущий B создаётся из этих согласованных данных и фиксируется на время открытия; явное обновление создаёт новую сессию. Снимки A/B никогда не пересчитываются по сегодняшним этапам. Заметки читаются через прежние подписки отдельно: это текущая редакция, а не историческая версия. Нет записи в БД, новых таблиц, изменений экономики или ZIP.

`app/comparison.ts` отменяет незавершённый инструмент и использует существующий `transition` с flush редактора. После ожидания очереди подтверждённой планировки выполняет чтение и повторную проверку epoch. Отказ сохраняет доступ к черновику. Refresh после последнего await дополнительно проверяет, что исходная сессия ещё активна: выход из режима не может быть отменён поздним результатом чтения. Импорт с новым epoch сбрасывает сравнение; RecoveryTray остаётся смонтированным вместе со своей защитой закрытия вкладки.

`CityCanvas` отделяет замороженные входные данные сравнения от liveQuery сцены. Материалы, включая изменения заметки из другой вкладки, не вызывают `CityEngine.update` (проверено инструментированием в браузере). Все три вида используют единственный PixiJS Application/canvas. На входе камера сохраняется с фактическим размером renderer; на выходе восстанавливается с поправкой на resize, без двойного смещения при закрытой панели. Фокус охватывает обе позиции изменённых объектов; его нижний предел масштаба согласован с ручным zoom — 0.03.

`comparison-art.ts` рисует отдельный слой с текстовыми значками. Снятые объекты и старые позиции имеют явные исторические контуры без hit testing. Список в `ComparisonPanel` обеспечивает доступ и к снятым объектам. Фильтр декора скрывает только маркеры/строки, не меняет выбранные визуальные состояния. События фильтруются по реальному владельцу и интервалу времён A/B; ссылки на материалы выводятся только через существующие `activityId`/`sourceActivityId` и `noteIds`. Текущие материалы владельца показаны отдельно. Совпадение по времени не объявляется доказательством причины изменения.

Readonly обеспечивается одновременно навигацией, панелями, редактором и callback-защитами canvas. `LayoutControls` не смонтирован, поэтому сочетания клавиш не вызывают undo/redo. Стеки планировки при входе/выходе не меняются. Нет восстановления исторического города, новых автоматических снимков или истории текстовых редакций.

## Планировка и история команд — 19.09.2026

`domain/roads.ts` строит четырёхсвязный маршрут между событиями указателя и определяет свободные/существующие/запрещённые клетки. Renderer хранит уникальные клетки текущего жеста в памяти; все промежуточные клетки видны до записи. Внешнее кольцо −1…40 позволяет показать выход за карту с ограниченным размером предпросмотра. Pointer capture, pointercancel/lostpointercapture и Escape завершают жест без частичного сохранения.

`storage/layout.ts` — отдельный LayoutService, используемый прежними командами CityService. Сериализует команды внутри вкладки, проверяет epoch, валидирует всю итоговую геометрию и связи, пишет изменения вместе с одним событием layout в единственной Dexie rw-транзакции. Существующие дороги пропускаются, остальные препятствия запрещают весь маршрут. DB остаётся источником истины; новые записи и события отсутствуют до отпускания указателя.

После успешного commit транзакции добавляется before/after только затронутых зданий/районов, максимум 100 команд в памяти. Undo/redo сверяет затронутые записи с ожидаемыми, повторно проверяет коллизии/уникальность учебного владельца и атомарно применяет обратную/прямую дельту. Ошибка не двигает стеки. Нет записи в tracks, learningObjects, notes, attachments, activities или snapshots; события прогресса не удаляются. Импорт меняет metadata.epoch, реактивное чтение сцены сбрасывает историю и активный инструмент; сама команда дополнительно проверяет epoch внутри транзакции.

`LayoutControls` читает стабильный внешний snapshot истории через useSyncExternalStore. Сочетания клавиш исключают input/textarea/select/contenteditable/textbox и исторический режим. Новые декорации получают отдельные ID; повторный режим включается только для нового декора, перенос и учебные здания одноразовые. Версия IndexedDB/архива и зависимости не изменены. Обычное сохранение формы оформления остаётся last-write-wins; обнаружение конфликтов значений в этой итерации добавлено для отмены/повтора.

## Границы и модули

Один локальный frontend и одна Dexie/IndexedDB база **progress-city-v1**. Имя базы сохраняется, текущая версия схемы — **2**. React отображает панели, Zustand хранит выбор и временный запрос результата, PixiJS 8 рисует через WebGL. Vite не получает материалы пользователя.

- `domain`: типы, награды, календарная дата, изометрия и пересечения; без React/PixiJS.
- `storage/db.ts`: версия схемы и транзакционные чтения; `migrate.ts`: чистая миграция v1 → v2, общая для БД и ZIP.
- `storage/service.ts`: транзакционные команды; `learning.ts`: исследования и расходы на их развитие.
- `storage/legacy-validation.ts`: исходная схема и проверки v1; `validation.ts`: строгая схема v2 и её связи; `backup.ts`: ограниченная распаковка и атомарная замена.
- `city`: renderer, векторная архитектура, камера и pointer-preview вне React. Запись только после подтверждённого размещения.
- `notes`: схема Tiptap, Blob node view, последовательная SaveSession, локальное восстановление.
- `features`: контекстные панели; `Research.tsx`: выбор исследования, вопрос/имя, основания и выбор развития.

## Модель

| Сущность | Ответственность |
|---|---|
| Track | Тема, тип, общий баланс, архивирование. stage используется привычками; у skill/project равен 1. |
| LearningObject | Исследование или мини-проект: имя, следующий вопрос, собственный stage 1–3, право строительства built, признак initial. |
| Building | Геометрия, шаблон, оформление и владелец. Снятие удаляет только размещение. |
| Note / Activity | Стабильные ссылки на направление и, для обучения, объект. Связанные материалы результата принадлежат тому же объекту. |
| ProgressEvent | Применённая сумма, версия правил, объект, при наличии sourceActivityId. |
| Snapshot | Копии зданий с историческими этапами и районов; не версии текстов заметок. |

Таблицы: cities, tracks, learningObjects, buildings, districts, notes, attachments, activities, events, snapshots, metadata. Идентификаторы не зависят от координат. Уникальный индекс `buildings.learningObjectId` исключает второе здание одного исследования; trackId больше не уникален. Для привычки одно здание обеспечивается сервисной транзакцией и проверкой архива. Декор не имеет владельца.

Первое исследование создаётся в одной транзакции с направлением и доступно бесплатно. Дополнительное исследование можно вести до покупки здания. После покупки и снятия здания право строительства сохраняется: повторное размещение, оформление и декор бесплатны. Связи существующих заметок, результатов и построек закреплены. Имя постройки и имя исследования можно менять независимо.

## Награды и расходы

Подтверждение в одной rw-транзакции читает актуальную активность, проверяет event ID, подтверждает запись, меняет баланс и добавляет событие. Для обучения ключ `activity:<id>`, для привычки `habit:<trackId>:<local-date>`. Конкурирующие вкладки сериализуются IndexedDB.

Улучшение использует `upgrade:<commandId>`, покупка — `construction:<commandId>`. Повтор одной команды не списывает снова; оплаченный объект нельзя купить повторно другой командой. Суммы расходов отрицательные, оформления — нулевые. Недостаточный баланс и ошибка записи откатывают всё, включая автоматический снимок. При наличии результат-основание принадлежит тому же направлению; объект может отличаться, поскольку баланс общий.

По умолчанию награды 1/2/3, этапы 3/6, строительство **3 очка**, согласовано пользователем. Новая версия правил применяется только к будущим событиям. При импорте баланс сверяется со всеми событиями направления, этап — с улучшениями конкретного объекта, built — с единственным событием покупки или правом initial. Исторический этап не может превосходить текущий.

`upgrade(trackId, commandId)` сохранён как фасад привычек и начального исследования. Новый UI использует `upgradeObject`. Уровень учебной постройки renderer получает только из LearningObject. Игровые этапы не являются объективной оценкой знаний.

Для привычек дата определяется Intl.DateTimeFormat в выбранной IANA-зоне. Дата, направление и часовой пояс закреплены при первом сохранении. Запись без достижения цели даёт 0; пропуски и честные записи не снимают очки. Полного пересчёта нет.

Снимки создаются при старте, после улучшения/оплаты строительства и вручную. Снимок оплаты предшествует выбору места; последующую планировку можно сохранить ручным снимком. Исторический вид недоступен для изменения, материалы открываются в текущей редакции.

## Миграция

Dexie version(2).stores(...).upgrade(...) добавляет learningObjects и меняет индексы внутри транзакции обновления. Каждое старое skill/project-направление получает один initial-объект с прежним stage; ID объекта равен ID направления (разные пространства сущностей), поэтому преобразование детерминировано даже для длинных импортированных ID. Здание, заметки, активности, события и здания снимков получают его ссылку. Track.stage становится 1, баланс и суммы событий не меняются. Исторические stage, epoch и Blob-вложения остаются прежними. Привычки не преобразуются.

Обычный экспорт — ZIP **v2**. Импорт принимает v1/v2. Для v1 сначала выполняются прежняя строгая валидация и проверка связей, затем миграция и полная проверка v2. В текущем формате отсутствующие поля не подставляются молча. Старое приложение несовместимо с новой схемой БД и ZIP v2; откат требует старого ZIP. Миграция проверена в fake-indexeddb и настоящей IndexedDB Chromium.

`prepareArchive` из `storage/archive-format.ts` проверяет весь будущий архив в экспорте, после разбора импорта, непосредственно перед `replaceCity` и внутри `version(2).upgrade` до записей. `encodeArchiveData` сохраняет предел **32 MiB UTF-8** для JSON, включая метаданные вложений и исключая Blob/epoch. Реальные `Blob.size` сверяются с полными метаданными, затем учитываются сами изображения, manifest и ZIP-служебная часть. Ошибка выходит из versionchange-транзакции: сохраняются прежняя версия/индексы и все таблицы. Ровно 32 MiB JSON и 64 MiB ZIP разрешены; превышение даже на байт отклоняется. Чистое преобразование `migrateV1` не менялось.

Расчёт точный для текущего `fflate.zipSync(files, { level: 0 })`: **22 + Σ(размер файла + 76 + 2 × длина пути в UTF-8)**, где в файлы входят `data.json`, все вложения и `manifest.json`. 76 — локальный заголовок 30 и запись центрального каталога 46; 22 — конец каталога. Нет сжатия, ZIP64, комментариев, дополнительных полей и data descriptor. Manifest строится одной функцией `encodeManifest` для допуска и экспорта: SHA-256 всегда занимает 64 ASCII-символа, дата — 24. В допуске используются хеши-заглушки той же длины; сериализация учитывает реальные размеры и пути. Сверено с [fflate 0.8.3, zipSync/wzh/wzf](https://github.com/101arrowz/fflate/blob/v0.8.3/src/index.ts) и фактическими архивами на границах −1/0/+1 байт. Смена формата ZIP требует пересмотра расчёта; экспорт дополнительно сверяет фактическую длину ZIP с рассчитанной.

Внутри versionchange нет чтения `Blob.arrayBuffer`, SHA-256, таймеров или других сторонних async-операций. После чтения таблиц допуск выполняет только синхронную сериализацию, чтение `Blob.size` и арифметику. Изображения и хеши по-прежнему проверяются при импорте/экспорте вне upgrade.

`MigrationRecovery` распознаёт конкретную ошибку лимита через обёртку Dexie и предлагает ZIP v1. `exportLegacyCity` открывает существующую БД без объявленных версий и upgrade, проверяет её версию, читает согласованный снимок в readonly-транзакции, валидирует прежнюю схему/связи и использует общий сборщик ZIP с прежними лимитами и SHA-256. Отсутствующая база не создаётся, текущая v2 не понижается. При уже превышенных старых лимитах или повреждении данных экспорт также честно отказывает; исходная база остаётся для прежнего клиента.

## Сохранение и конфликты

Источник заметки — Tiptap JSON, поисковый текст выводится из него. SaveSession сохраняет последовательно, включая ввод во время записи. Переходы ждут flush и загрузку изображения; ввод временно блокируется. Проверка revision внутри транзакции защищает от потери чужой редакции. Отдельная копия создаётся атомарно; повторный клик и поздняя картинка проверены.

metadata.epoch меняется при восстановлении ZIP, не входит в архив и защищает старые редакторские сессии, копии и изображения даже при совпадении ID/revision. Редактор заранее получает исходные Blob в транзакции с epoch. Node view создаёт и освобождает временные URL; в БД они не записываются.

Если редактор исчезает или меняется epoch, несохранённая SaveSession и исходные изображения остаются в RecoveryTray независимо от панели/Loading. Их можно выгрузить отдельным ZIP (note.txt, note.json, attachments.json и изображения). Это ручное спасение материала, не импорт города. Черновик находится только в памяти вкладки; закрытие/сбой процесса может его потерять.

Переход «Зафиксировать результат» завершает flush, проверяет исходный epoch и передаёт краткий ResultRequest с ID, сохранённым заголовком и epoch. Форма не зависит от задержки публикации liveQuery. Имя/вопрос исследования сохраняются с исходным epoch и сравнением исходных полей внутри транзакции. При конфликте ввод остаётся до явной загрузки актуальных полей.

Подписки оболочки разделены по таблицам; каждая читает epoch в той же транзакции. Панели получают данные только при совпадении всех epoch. CityCanvas читает только город, направления, учебные объекты, размещения, районы и выбранный снимок. Автосохранение заметки не вызывает CityEngine.update или пересоздание сцены.

## Архив и безопасный ввод

ZIP: manifest.json с форматом/версией/временем, размерами и SHA-256; data.json с сущностями и метаданными вложений; attachments/<id> с исходными байтами. SHA-256 обнаруживает повреждения, не является подписью/шифрованием. Экспорт читает согласованный снимок таблиц, затем обрабатывает Blob.

Общие пределы в limits.ts: ZIP 64 MiB, распаковка 128 MiB, manifest 1 MiB, data 32 MiB UTF-8, изображение 5 MiB; до 1002 файлов. Распаковка кусочная, проверяются реальные объёмы, пути, дубликаты, размеры, хеши, схема, ссылки, геометрия и журнал. Замена очищает/заполняет все таблицы в одной транзакции и обновляет epoch; ошибка сохраняет прежний город. До замены UI предлагает экспорт и просит подтверждение.

Максимумы: 1000 направлений, 5000 исследований, 1600 размещений, 200 районов, 5000 заметок, 1000 вложений, 20 000 активностей, 50 000 событий, 1000 снимков. Документ: до 200 000 символов текста, 20 000 узлов, глубина 30. Экспорт за пределами ограничений отклоняется без изменения БД. Настройки показывают объёмы и предупреждение от 80%; неиспользуемые изображения автоматически не удаляются.

Разрешены PNG/JPEG/WebP с проверкой сигнатуры. Документы проверяются allowlist и той же ProseMirror schema.nodeFromJSON().check(), что используется редактором. Произвольные HTML/SVG, удалённые изображения и исполняемый код не принимаются. URL допускают только http/https/mailto.

## Среда и источники

Исправление миграции проверено на Node 22.23.2, локальном npm 12.0.2, Windows; предыдущая итерация кварталов — на Node 24.19.0. Точные версии зафиксированы в package-lock.json: React 19, Vite 8, TypeScript 6 strict, PixiJS 8, Tiptap 3, Dexie 4, Zustand 5, Vitest 5, Playwright 1.63. Новых зависимостей в этой итерации нет. Docker и внешние сервисы не использовались.

Проверены [Dexie — Version.upgrade](https://dexie.org/docs/Version/Version.upgrade()), [Dexie — transactions](https://dexie.org/docs/Dexie/Dexie.transaction()), ранее — [Vite](https://vite.dev/guide/), [PixiJS 8](https://pixijs.com/8.x/guides/components/application), [Tiptap React](https://tiptap.dev/docs/editor/getting-started/install/react). Используются API установленных версий.

Архитектура города — собственные векторные рисунки art.ts, без внешних ассетов и шрифтов. Скриншоты содержат только синтетические данные; тестовая галерея не является стартовым городом.
