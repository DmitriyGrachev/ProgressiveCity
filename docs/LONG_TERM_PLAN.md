## Дизайн и границы

1. **Страховка ввода.** Одна CityDB; новая версия3 добавляет вспомогательные stores recovery/recoveryAttachments/clientState. Импорт заменяет явный список городских таблиц, не журнал/локальное состояние. UUID ветки редактора, исходный epoch/revision, последовательный seq и условная очистка защищают две вкладки и поздние saves. Запись журнала происходит во время работы, не в unload. Статус защиты появляется только после commit; ошибка оставляет текст/выгрузку. Note/Blob сохраняются без blob URL. Восстановление — явное действие, один существующий редактор/форма, без автоматического подтверждения/наград и без записи поверх другого epoch.
2. **Библиотека и резервирование.** Очистка только явная: предпросмотр ID/объёма, повторная проверка ссылок и epoch в транзакции, защита материалов и recovery. Удаление не касается заметок/истории/результатов. Свежесть копии подтверждает проверка выбранного пользователем сохранённого архива, а не click/download; stamp связан с epoch и каноническим содержимым. После изменения города копия устаревает. Новая ZIP3: bounded256MiB/expanded512MiB, JSON32MiB и5MiB на изображение остаются. ZIP1/2 сохраняют прежние64/128MiB. V3 writer обрабатывает изображения последовательно через установленный fflate, без массива всех исходных Uint8Array. Пределы материалов остаются прежними. Проверить реальный round-trip >64MiB, отказ/целостность и отзывчивость; не обещать неограниченный объём.
3. **Жизнь привычки после3.** Активная habit/reduce на этапе3 покупает сад(park), двор(plaza), павильон(pavilion) за rules.constructionCost. Владение — отдельное структурированное immutable событие habitAddition с additionKind; additionId=event.id, Building.habitAdditionId ссылается на покупку. Не LearningObject, без отдельной валюты/этапа4. Атомарные расход/event, idempotent command ID, epoch и реальное положительное activity-основание. Приобретение отдельно от размещения; Escape/снятие/undo не отменяют покупку. Один оплаченный ID — один объект карты; повторное размещение бесплатно. Бесплатный декор не меняется. Принадлежность и основание видимы; карта/preview/snapshot используют этап1 дополнения, основной дом остаётся3. A/B сопоставляет additions по их ID и сохраняет read-only.

Новые зависимости/backend/облако/AI/автоподтверждения/штрафы/автоматическое удаление не входят. Пункт4(настоящий многодневный пилот) и «Связный квартал» не выполняются этой итерацией. Личный5173/профиль/prepared.json не используются в проверках. ZIP/логическая модель честно переходят на3 с приёмом старых1/2, физическая миграция только добавляет stores без переписывания старых строк.

Альтернативы: отдельная RecoveryDB проще изолирует импорт, но выбрана одна БД с явным списком таблиц; отдельная сущность владения не нужна, поскольку покупка неизменяема и уже имеет собственный event; повышение общего глобального лимита отклонено, чтобы не ослаблять legacy/materials. Это технические решения исполнителя. Продуктовая цена и виды дополнений подтверждены пользователем.

## Review focus

- Новый journal seq/revision не удаляется поздним успешным save; одна вкладка не очищает ветку другой.
- Импорт с теми же ID не принимает старые тексты/attachments как данные нового города и не очищает журнал.
- Изображение страхуется до основной записи; ошибка журнала видима, незавершённая операция не называется сохранённой.
- Cleanup повторно вычисляет ссылки перед удалением; stale preview и другой epoch отклоняются; ZIP3 admission не ломает старые форматы/лимиты материалов.
- Покупка имеет стабильный ID/стоимость/основание, не отменяется планировкой и не превращает все здания привычки в один A/B объект; stage1 дополнений не подменяется stage3 владельца.
